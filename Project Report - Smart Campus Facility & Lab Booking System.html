2. Introduction

In modern university ecosystems, academic infrastructure is heavily shared across multiple faculties, research laboratories, student associations, and sports clubs. These facilities encompass high-performance GPU computing clusters, IoT research facilities, multimedia seminar halls, grand auditoriums, and recreational sports grounds.

Without an automated scheduling mechanism, campuses experience frequent double-booking collisions, resource hogging, and unauthorized reservations. The Smart Campus Facility & Lab Booking System was conceived as a console-driven, robust software application built strictly in Java SE. It enforces strict time-interval overlap validation, applies polymorphic booking policies depending on user roles (Student vs. Faculty), and maintains persistent state in a structured flat file database.

3. Problem Statement

Traditional campus facility booking relies on physical logbooks, paper slips, or ad-hoc emails. This conventional workflow exhibits multiple structural flaws:

  • Simultaneous Collisions: Multiple user groups often arrive at the same facility having received verbal approval for overlapping slots.
  • Resource Monopolization: Students reserve specialized computer laboratories for entire days without duration caps, denying access to peers.
  • Unauthorized Bookings: High-capacity auditoriums require institutional endorsements, yet lack automated permission barriers.
  • Disjoint Historical Records: Absence of centralized data leads to scheduling disputes and inability to analyze resource utilization.

4. Functional Requirements

The system is architected around three major functional modules:

Module 1: Facility Catalog & Schedule Explorer

  • Maintains polymorphic representations of physical campus facilities: Lab, Hall, and SportsCourt.
  • Displays detailed hardware, seating, and amenity specifications for each facility.
  • Queries date-filtered schedules showing active confirmed bookings in chronological order.

Module 2: Reservation & Collision Resolution Engine

  • Validates user existence, operating hours (07:00 to 22:00), and non-inverted timestamps.
  • Implements algorithmic interval overlap detection: start1 < end2 && end1 > start2.
  • Enforces role-based session quotas: Students max 2 hours; Faculty max 6 hours.
  • Restricts direct grand auditorium bookings to authorized faculty members.
  • Provides booking cancellation that immediately frees the vacated interval.

Module 3: Campus Analytics & Reporting

  • Aggregates total facilities, registered users, and active vs. cancelled bookings.
  • Calculates real-time booking frequencies per facility using Java Streams.
  • Groups and displays campus-wide activity by academic department.

6. System Architecture

The software follows a classical 3-Tier Layered Console Architecture entirely encapsulated within standard Java:

  • Presentation Tier (CLI Controller): Handles console I/O, user session state, interactive menus, and non-interactive command line flags (--test, --demo).
  • Business Logic Tier (Core Engine): Enforces interval overlap validation, duration limits, permission gates, and usage analytics.
  • Data Access Tier (Persistence Layer): Handles flat-file serialization and deserialization against campus_data.txt using buffered character streams.

8. Design Decisions & Rationale

  1. Single-File Main.java Architecture: Eliminates package declaration and classpath mismatch issues when evaluating across varied operating systems (Windows Command Prompt, PowerShell, Linux Bash).
  2. Zero Third-Party Dependencies: Guarantees that the project compiles on any standard JDK 17+ environment without downloading external `.jar` packages.
  3. Flat Text Database (campus_data.txt): Human-readable pipe-delimited format allows evaluators to directly inspect data in Notepad without installing dedicated database engines.
  4. Mathematical Interval Overlap Logic: Uses boundary verification start1 < end2 && end1 > start2 to detect overlaps while cleanly permitting back-to-back bookings.

9. Implementation Details

The system models domain rules using core Java OOP principles:

  • Dynamic Polymorphism: Method getMaxBookingHours() is invoked uniformly on User references, dynamically executing the subclass implementation (Students restricted to 2 hours, Faculty allowed up to 6 hours).
  • Defensive Encapsulation: All model fields are private. State mutations (e.g. changing maintenance status, cancelling bookings) occur through validated methods.
  • Custom Exception Hierarchy: Checked exceptions (CampusBookingException, SlotUnavailableException, InvalidInputException) cleanly communicate rule violations back to the CLI layer.

12. Challenges Faced

  • Interval Boundary Conditions: Ensuring that contiguous back-to-back bookings (e.g., slot 1 ending at 12:00 and slot 2 starting at 12:00) do not trigger false-positive collisions.
  • Test Idempotency: Designing automated tests to remain repeatable across multiple test executions without polluting persistent seed data.
  • Buffer Handling in Scanner: Handling newline consumption issues when switching between numeric inputs and full-line strings.
