1. Abstract

In an academic campus environment, shared infrastructure including high-performance computing labs, specialized hardware research centers, seminar halls, and sports arenas experience frequent scheduling bottlenecks and booking collisions.

This project implements the Smart Campus Facility & Lab Booking System, a lightweight, highly reliable terminal application developed entirely in standard Java. The software leverages Object-Oriented Programming (OOP) principles to represent polymorphic facilities and user profiles, enforces mathematical interval-overlap conflict detection, implements role-specific quotas (students vs. faculty), and persists data within a single-file text database (data/campus_data.txt). Both an interactive console menu and non-interactive command-line flags (--test, --demo) are supported to ensure compatibility with automated evaluation scripts and manual grading alike.

2. Problem Statement & Objectives

2.1 Problem Statement

University departments and student clubs require access to campus resources. Without a centralized, rule-enforced booking engine, problems such as double-booking identical time slots, students over-reserving lab resources, and unauthorized auditorium bookings occur frequently.

2.2 Objectives

  • Pure Java Implementation: Zero third-party dependencies; compiles instantly using standard javac.
  • Core OOP Compliance: Full demonstration of Abstraction, Inheritance, Polymorphism, and Encapsulation.
  • Conflict Prevention: Algorithmic verification of requested intervals against active reservations.
  • Single-File Persistence: Flat text-file database utilizing human-readable pipe-delimited records.
  • Automated Evaluator Compliance: Non-interactive --test flag executing self-diagnostics with exit codes.

3. Object-Oriented System Architecture

3.1 Hierarchy of Classes

  • Facility (Abstract Base): Represents shared physical campus locations.
    • Lab: Includes workstation count, operating system, dedicated GPU specifications.
    • Hall: Covers seating capacity, A/V systems, projectors, and air conditioning.
    • SportsCourt: Specifies indoor/outdoor nature, surface type (synthetic, clay, wood), and floodlights.
  • User (Abstract Base): Models individuals interacting with the campus booking engine.
    • Student: Constrained to a 2-hour maximum booking session to prevent resource hogging. Direct grand auditorium bookings restricted.
    • Faculty: Granted extended 6-hour research/seminar reservations and direct auditorium access.
  • Booking: Immutable record storing reservation identity, user ID, facility ID, date, start/end times, status (CONFIRMED, CANCELLED), and purpose.

4. Core OOP Principles Applied

OOP Principle Implementation in Project
Abstraction Abstract classes Facility and User define base signatures (getSpecificDetails(), getMaxBookingHours(), canBookAuditoriumDirectly()) hiding low-level details.
Inheritance Lab, Hall, and SportsCourt inherit core attributes (id, name, capacity, location) from Facility. Student and Faculty inherit from User.
Polymorphism Dynamic method dispatch handles user quota limits: student.getMaxBookingHours() returns 2, whereas faculty.getMaxBookingHours() returns 6.
Encapsulation All class attributes are declared private or protected with validated getter and setter accessors.
Exception Handling Custom domain exceptions (BookingException, SlotUnavailableException, InvalidInputException) safely handle business-rule violations.
